# 题目 7 验收清单

> 当前 Docker PostgreSQL 验收基线使用题目要求的三个预置项目；容器使用 named volume `110_team-recruitment-data`。历史临时验收项目已清理。

## 测试素材

- `alice / demo1234`：项目发起人
- `bob / demo1234`：申请人
- `cathy / demo1234`：竞争申请人
- `david / demo1234`：无关用户和第二申请人
- `校园智能导览`：招募中，前端角色 1 个名额，bob/cathy 两条待审核申请
- `绿色校园能耗看板`：暂停招募
- `社团活动协作台`：后端角色已满

## TEAM-01 项目发布与筛选

- 操作：用 alice 发布一个角色、技能和人数完整的新项目；用关键词、角色、多个技能组合筛选。
- 预期：项目真实写入数据库；筛选条件为 AND；角色和技能匹配同一个角色；详情显示进展、成果和余量。
- 实际结果：通过。alice 可发布包含多个角色的项目；项目详情返回发起人成员、角色和真实余量；使用项目标题、角色和 `React,TypeScript` 技能组合筛选时，条件按 AND 生效且技能匹配同一角色。

## TEAM-02 申请规则

- 操作：用 bob 申请开放项目，重复申请一次；尝试申请自己的项目、暂停项目和已满角色。
- 预期：成功申请产生一条待审核记录；重复申请、自己项目、暂停项目、满员角色均由后端拒绝。
- 实际结果：通过。Docker PostgreSQL 中 bob/cathy 均创建待审核申请；重复申请返回 `409 PENDING_APPLICATION_EXISTS`；alice 申请自己的项目返回 `403 OWNER_CANNOT_APPLY`；已满角色返回 `409 ROLE_FULL`；暂停项目新申请返回 `403 RECRUITMENT_PAUSED`。

## TEAM-03 撤回与重新申请

- 操作：提交申请，撤回，再重新申请；让发起人拒绝新申请并填写原因，再次重新申请。
- 预期：旧记录保留；状态分别为 withdrawn/rejected；新申请是独立记录；拒绝原因可见。
- 实际结果：通过。Docker 中 david 提交申请后撤回，状态为 `withdrawn`；重新申请生成新记录；alice 拒绝新申请并保存原因“需要更多用户访谈经验”；david 在“我的申请”读取到 `rejected` 和拒绝原因，之后再次申请返回 `201`，历史记录保留。

## TEAM-04 单名额并发审核

- 操作：alice 在两个浏览器会话同时接受 bob/cathy 的前端申请。
- 预期：最终最多一个成员；角色余量为 0；成功申请为 approved，失败方仍为 pending 并得到名额已满提示。
- 实际结果：通过。Docker PostgreSQL 两个并发接受请求返回 `200` 和 `409`；最终角色 `joinedCount=1`、`remaining=0`；两个申请状态为 `approved,pending`，没有超额成员。

## TEAM-05 重复审核

- 操作：对同一个申请连续或并发点击接受。
- 预期：一条成员记录、一个席位；重复请求返回已处理或明确冲突，不重复加人。
- 实际结果：通过。对同一已通过申请再次接受返回 `200` 且 `alreadyProcessed=true`；成员列表只保留一条该用户成员记录，角色只占一个席位。

## TEAM-06 暂停招募

- 操作：alice 暂停项目；旧待审核申请继续审核；普通用户提交新申请；恢复后再次提交。
- 预期：暂停只阻止新申请，不阻止审核已有申请；恢复后仅有余量角色可申请。
- 实际结果：通过。对“绿色校园能耗看板”执行暂停/恢复接口返回 `200`；暂停期间 david 新申请返回 `403 RECRUITMENT_PAUSED`；恢复后仍有余量的角色可继续申请，已有申请不会因暂停被删除。

## TEAM-07 暂停后恢复与满员角色

- 操作：暂停一个仍有名额的项目；恢复后让用户申请一个已经满员的角色。
- 预期：暂停期间拒绝新申请；恢复不会重置已加入成员或名额，满员角色仍拒绝申请。
- 实际结果：通过。后端按当前角色余量重新校验，恢复招募不会绕过满员约束。

## TEAM-08 撤回与接受并发

- 操作：让申请人撤回与发起人接受尽量同时提交。
- 预期：最终只能是已撤回且未加入，或已通过且已加入；不能出现撤回但占用名额。
- 实际结果：通过。申请行锁保证状态转换为单一终态，失败请求返回状态已变化。

## TEAM-09 权限和正文隔离

- 操作：bob/cathy/david 调用 alice 项目的审核接口和申请列表；普通用户读取他人项目详情。
- 预期：不能审核；不能读取他人申请正文；公开项目目标、角色和成员仍可读取。
- 实际结果：通过。普通用户审核接口返回 `403`；非发起人读取项目全部申请返回 `403`；普通用户项目详情只返回自己的申请正文，不能读取其他申请人的 reason/contribution；公开项目目标、角色和成员仍可读取。

## TEAM-10 资料快照

- 操作：bob 提交申请后修改昵称、简介、技能和时间；alice 查看旧申请。
- 预期：旧申请显示提交时快照，新申请使用最新资料。
- 实际结果：通过。Docker 中 bob 提交后修改个人资料，alice 看到的旧申请仍保留提交时昵称、简介、技能和每周投入时间；后续新申请使用更新后的资料。

## TEAM-11 持久化

- 操作：创建项目、申请、审核成员后执行 `docker compose down`，再执行 `docker compose up -d`。
- 预期：项目、申请、成员、审核状态和角色余量保持一致。
- 实际结果：通过。执行 `docker compose down`（未使用 `-v`）后再次 `docker compose up -d`；app 重新启动，db 显示 `healthy`，健康接口返回 `200`；测试项目仍可读取，重建后读取到成员 2 条、申请 4 条、角色余量保持一致。

## TEAM-12 交付验证

- 命令：`npm run build`、`npm test`、`docker compose up --build`。
- 预期：测试通过，镜像构建成功，应用可访问，初始化自动完成。
- 实际结果：上次 Docker 记录为 31/31；本轮修改后需在验收环境重新执行 `npm test`、`npm run build` 和 `docker compose up --build -d`，并记录新的测试数量与并发结果。
